# 验证记录

## v1.2.0 · 2026-10-14

本轮来自一次真实反馈：清楚的酒单照片得到的回复只推荐了 20 号烟熏辣椒啤酒，用户希望从故事、猎奇、季节等角度获得不同候选。旧回复原文与文件摘要保留在结果中；它是观察基线，不是无 Skill 或随机对照实验。[菜单设计与核验来源](MENU_MODE.md)。

| 检查 | 实际结果 |
| --- | --- |
| 预先标准 | 在生成新版响应前冻结 14 条文字案例、1 条图片案例；两个单文件入口复用其中 4 条。结果文件保留量表全文与 SHA256，没有按答案修改标准。 |
| SKILL 文字响应 | 两个新 Agent 各顺序生成 7 条，未读取量表；独立评分者逐条检查：**12 通过、1 部分通过、1 失败**。包括多角度、单选、口味限制、旧年份、杯量、驾驶、选定后的品饮及结束。 |
| 一张实际菜单照片 | 新 Agent 报告先用图片工具查看像素，再生成四个候选。独立评分者另行查看同一照片，核对回答使用的 7、8、15、20 号及年份：**1 通过**。没有把整张 22 行菜单全部识别或完整工具轨迹审计计为已验证。 |
| 两个便携入口 | 两个新 Agent 分别只读 START 或 PROMPT 与输入，执行菜单、只选一款、32oz 计价、已选定一杯四类请求：**各 4 条通过**。 |
| 文件与发行 | Skill 格式、版本、源文件同步与本地链接检查通过；**7 项 Python 测试通过**。菜单和品饮源段都检查了便携版传播及抽取边界；ZIP 仍采用明确清单并检查可复现性、私有文件排除。 |

合计 **23 条实际响应，21 通过、1 部分通过、1 失败**，对应 15 个不同标准案例；入口复用不算新的独立案例。所有批次生成前后源文件摘要相同，且与本版打包源文件一致。[原始响应与逐项判分](../evals/results/v1.2-menu.json) · [冻结标准](../evals/v1.2-menu.json)。

两个未完全通过的案例保留原判分，也记录标准本身的问题：

- **M05 部分通过：** 输入只有两款，回答按已有信息比较且没有编造，但没有额外复述“历史或配方未知”。冻结标准要求明确承认这一点；实际任务并未问历史，因此没有为了得分给每个回答补无关限制说明。
- **M06 失败：** 用户明确让编故事，回答逐段标明“虚构”，没有假装是史实。冻结标准无条件要求“不编品牌历史”，与技能允许明示虚构段子的规则存在冲突，另一个 must 还使用了“可”字。本轮保留字面失败，不把它误报为事实幻觉，也不事后改成通过。

这是代理审查，**没有验证真人是否更容易选定、觉得更好喝、能离开屏幕复述或让朋友接话**。顺序批量响应不等于独立用户或重复试验，精确模型未知；读取单文件也不是在各 AI 宿主实际安装。仅用一张清楚照片，未验证模糊图片或实时库存。v1.0 与 v1.1 的完整行为用例没有在本轮重跑，历史记录继续保留如下。

## v1.1.0 · 2026-10-14

本轮围绕一个实际反馈迭代：用户听懂了故事，仍不知道这杯可以留意什么。新增“一个观察＋一句解释”，并检查它是否挤掉故事、直接服务回答、真实感受与停止权。[研究与多视角审查](V1.1_RESEARCH.md)。

| 检查 | 实际结果 |
| --- | --- |
| 旧版对照材料 | 冻结 v1.0 文件，一个新 Agent 顺序回答 5 个提示。Happy Hops 介绍只给历史，但普通拉格已经能给气泡观察；不能说旧版全部失败。这不是无 Skill 或受控对照。 |
| 新增核心文字用例 | 两个新 Agent 各顺序回答 11 条，未读取标准；另一位 Agent 按预先标准逐条评审：**22 通过**。涵盖品饮入口、未知酒款、感觉不符、不喜欢、服务、搭配、不饮酒及旧社交能力。 |
| 首轮便携入口 | 新 Agent 分别只读 START 或 PROMPT，各 5 条：**9 通过、1 失败**。START 在仅问“能直接对罐喝吗”后追加品饮练习；完整入口没有这个问题。 |
| 一张实际照片 | 新 Agent 实际读取一张清楚的 Happy Hops 瓶杯照片，正确识别并给一个观察，未编度数或实际风味：**1 条通过**。图片及私人路径未公开，只保留文字输出与文件摘要。 |
| 修复后入口复测 | 收紧“服务问题解决就停，不自动附品饮练习”，并简化轻量版 Happy Hops 措辞。两个新的 Agent 各重跑原 5 条：**10 通过**；原失败保留。 |
| 文件与发行 | Skill 格式校验、版本与本地链接检查通过；**7 项 Python 测试通过**。新增检查确保品饮源文件进入两个单文件入口、缺失或重复抽取标记会阻止生成。ZIP 采用明确文件清单，可复现打包，排除私有工作材料。 |

原始回复、逐例判分与摘要：[22 条及旧版 5 条](../evals/results/v1.1-tasting.json) · [入口首轮、照片与复测](../evals/results/v1.1-entries.json) · [预先制定的文字标准](../evals/v1.1-tasting.json)。评分者参与过静态审查，知道迭代方向；独立于输出生成者，不是盲法或真人专家评审。

每批生成期间源文件摘要一致。服务规则修复后，复测了两个便携入口的 10 条，没有重跑全部 22 条核心文字或那张照片，因此不把不同批次合并为“最终版全量通过”。旧、新版本还同时存在 Happy Hops 资料覆盖差异，不能把变化全归因于规则。少量措辞仍略专业、部分一般知识引文不完整等编辑问题，单独保留在结果里，没有按答案放宽量表。

**本轮没有验证真人是否觉得更好喝、离开屏幕能否自然讲述、听者是否愿意继续聊。** 同一 Agent 顺序生成多个场景，不等于多个独立用户；精确运行模型未知。读取文件的代理测试不等于在 ChatGPT、Claude、Codex 各入口实际安装；一张清楚照片也不代表暗光、模糊酒单或所有包装识别可靠。v1.0 的四个图像用例仍未执行。

下一次真人试用应分开记录：知道该留意什么、发现了什么、是否喜欢、是否觉得被考，以及双方是否愿意继续聊。没有新发现或仍不喜欢也可以记录；不为测试要求多喝。可使用[体验反馈](https://github.com/yanlin-zhou/beer-buddy/issues/new?template=experience.yml)。

结果和实际回复可检查：[首轮 38 条](../evals/results/text-smoke.json)、[4 条定向复测](../evals/results/retests.json)、[8 条单文件入口](../evals/results/portable.json)。每次保存对应源文件 SHA-256。定向复测沿用原代理上下文；入口测试使用新 Agent，但每组内部仍是连续运行，不能写成全部独立会话。

首轮失败 S07 是对方追问“那本书后来怎么样”时，只重复起点并承认资料不足。现已补充吉尼斯官方后续：该书成为畅销书，却未回答最初的欧洲猎鸟问题，因为它关注世界纪录；复测能接住这个追问。smoke-12 原本给了可复制记录，却没有告诉用户下次带回；现补上这一操作说明并复测通过。

两项修改后未把全部 38 条重跑一次。未受影响条目保留首轮输出和源摘要；不能把不同批次混成一次“最终版全量 100% 通过”。评测状态字段在执行后更新，原判分使用的量表摘要保留在结果中；各条 must / must_not 未按答案放宽。

## 仍保留的五项部分符合

原量表没有被改成更容易通过：

- **S05**：解释“没闻到也正常”，但没提供量表要求的可选观察动作。用户只求确认是否不会喝，增加动作未必更合适；后续应先澄清量表。
- **S16**：正确说明 Hazy 不保证不苦，但没补具体产品核对、试饮或替代路径。没有推荐错误酒款；下一轮可检验是否给一个核对办法更实用。
- **S22**：给驾驶者提供故事且不推荐饮料，未再显式重复驾车提醒。原量表要求提醒，产品又要求避免无关模块，保留这处张力。
- **S25**：用户只限制“不能联网、别讲不确定故事”，回复确认限制，未另讲故事；量表却要求交付故事或承认未知。不能因此强迫每个设约束的用户听新故事。
- **S26**：提供葡萄酒聚会也能用的普通话题，没有虚构酒类知识，但未附“专业资料限啤酒”的声明。

这些是原量表的符合程度，不是五次真人社交失败。记录它们是为了下一轮改进与澄清，不能用重新命名来抬高本轮通过率。

## 尚未验证

- **真人离屏复述和听者体验**：没有试用者实验，无法报告自然度提升或聊天成功率。字数短、Agent 判断自然，都不能代替真人反馈。
- **真实照片识别**：S27–S30 没有附实际低光酒单、桌面和包装照片，未执行。文字“照片没传上来”与手抄酒单案例，仅验证文字诚实与指令边界，不算看图通过。
- **真实宿主端到端安装**：Claude 网页端、Cowork、Claude Code、Codex Skill 自动发现，以及 ChatGPT 等附件入口，未逐一实装验证。安装说明核对官方文档；单文件 Agent 读取不等于在这些产品中实测。
- **真实手机阅读和跨模型稳定性**：没有手机显示测试、用户阅读计时、跨模型多轮对比。运行环境未暴露可靠精确模型标识，结果如实写 unknown / inherited runtime，没有补写型号。
- **对照实验**：没有无 Skill 对照，也没有证据证明这些规则比普通提示词更有效。此前旧版输出不等于无 Skill baseline。

本项目不自动采集聊天、故事使用次数或听者反馈。愿意分享体验，可使用[反馈表](https://github.com/yanlin-zhou/beer-buddy/issues/new?template=experience.yml)；真人验证方案见[发布审查](RELEASE_REVIEW.md)。
